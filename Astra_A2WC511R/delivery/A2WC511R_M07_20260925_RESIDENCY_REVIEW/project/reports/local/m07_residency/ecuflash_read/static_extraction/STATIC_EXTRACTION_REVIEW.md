# Installed ECUFlash static extraction probe

**The installed Read implementation and exact DUAL kernel remain unresolved.** This probe did identify the protection format and statically recover two loader layers; it did not stop at absent strings or entropy. It does not show that further reverse engineering is impossible.

The immutable installed executable is SHA-256 `5e1b1729446d306487bb7ed358b1ee050b11e440902bb23a05663d8575346115`. Every operation used an identical disposable copy as data. ECUFlash, its provider and the recovered code were never loaded or executed. The only programs run were local analysis tools and Python byte-buffer transformations.

`pe_details.json` records six sections, exact raw/virtual bounds, exports, entry bytes and signature-marker searches. The image has 93 FTDI API exports, a TLS directory with an empty callback list, and a two-function import table. The entry RVA `11D9000` begins `56 50 53 E8 01 00 00 00 CC 58 89 C3`. The first executable section expands from 5,956,608 stored bytes to 12,648,448 virtual bytes; a later section reserves 4,177,920 bytes with only 512 stored bytes. These are concrete loader characteristics, not a standalone proof based on entropy.

The available 7-Zip 26.02 recognized a PE file and listed its sections, certificate, icon, icon group and manifest. It found no embedded archive or kernel resource. No local UPX or Detect It Easy executable was found in the inspected development/tool roots. A side-by-side official [Detect It Easy 3.21 portable release](https://github.com/horsicq/DIE-engine/releases/tag/3.21) was installed under `work/tools/m07_die321`; archive SHA-256 is `078f2934f267392247f9c7b759a1c2457a48bc2000b25b80c2f129955ee4a3b9`. Its local deep/heuristic scan exited successfully and identified **Themida/Winlicense 1.XX–2.XX**. The pinned `protector_Themida.2.sg` rule uses the import-position signatures for that reported version. No exact protector minor version is claimed. No UPX strings were present; a UPX decompression attempt was not appropriate to this identified format. The scanner's help option opened a help dialog; its owned process was closed before the actual successful scan. It did not launch the target.

The actual entry stub provides an explicit transform for the first 4,096 bytes at RVA `1010000`: each little-endian longword becomes `((word XOR 5E947B85) + 2D52015D) mod 2^32`. `static_decode.py` asserts the source instruction bytes, applies that transform to a byte buffer and proves the inverse round-trip. The decoded block hashes to `bb72acc24e9bf4b83358e71230462c4a1738b9d40d53d0710756d09420c7d1e8`.

That block calls an aPLib-compatible decompressor at VA `014100BF` with input RVA `1010212` and output RVA `C14014`. The bounded Python translation consumed **1,860,492 bytes**, producing **4,173,012 bytes** within the reserved section. Output SHA-256 is `7f01029e62b1e337413ae587716026c312a12dc7f265b7962bf0130499fa2539`. A separately downloaded, source-reviewed [aPLib implementation](https://github.com/snemes/aplib/tree/38f856ea7f0cdc31258d88165858051f71c03d84) produced exactly the same bytes and consumed the same input length. Its source, license and provenance are retained under `work/tools/m07_aplib`. Truncation and undersized-output controls both fail as required.

The recovered loader contains the literal `Themida` at offset 5,097. Its first jump reaches VA `0101577D`. The next explicit loop at `01015955` subtracts one from 28,672 bytes beginning at `01015966`; applying only that arithmetic yields SHA-256 `30e96f024c0c11c82b7b4193d47713af7ae300d7c8508299938501a51959926e`. Source bytes, bounds and output are recorded. This is still a protection loader, not a recovered application executable or SH kernel.

The next inspected control flow installs exception handlers through `FS:[0]`, uses generated code and saved-context modifications, and intersperses code with deliberately skipped data. For example, handler `01015ADF` changes a context field at offset `B0`, and handler `01015AF2` rewrites the field at offset `B8`; no Windows exception model or application startup was run. The original application sections, imports and exact Read/kernel selection logic have not been reconstructed. Continuing requires a larger protector-specific static/control-flow recovery effort or a separately isolated and audited execution model. Treating this loader as the actual Read implementation would be false evidence.

This addendum does not change the earlier historical findings: recorded DUAL V1.07 uploads were 4,660 bytes at `FFFF3000`; historical read logs leave 434,176 image bytes without explicit read coverage; the unrelated FastECU reference kernel is 6,056 bytes and has independently observed RAM clearing. None of those facts identifies the installed embedded kernel, proves complete current-ROM acquisition, excludes flash commands from its Read initialization, or proves cleanup/reset behavior. Those gates remain FAIL. The old native A0 full-image attestation remains withdrawn.

Reproduce the bounded decode with `static_decode.py` using the pinned local analysis dependencies. `die_scan.stdout.json`, `7zip_listing.txt`, `static_decode.json`, `aplib_crosscheck.json`, entry/exception disassemblies and the extraction manifest preserve the evidence. No physical procedure is approved by this result.
